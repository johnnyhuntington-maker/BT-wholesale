Summary

The gap analysis ran on 24 Jul 2026 against the RBAC PRD (Section 17.5, Section 17.6, Section 17.9, Section 17.10), the RBAC-intel.md doc, and the wholesale.html prototype. On 27 Jul 2026, a second pass was run against the Customer Establishment swim lane (Deepa Packirisamy), adding 16 further findings — all implemented the same day.
All 27 actionable gaps have been implemented. The prototype is now current with everything derivable from the PRD, RBAC-intel.md, and the Customer Establishment swim lane.
The prototype is a single-file React UMD prototype at wholesale.html. It's a design and stakeholder tool — not production code. Decisions made here inform the Salesforce RBAC implementation.

Swim lane findings — 27 Jul 2026

16 findings from the Customer Establishment swim lane (Deepa Packirisamy). All implemented in a single session on 27 Jul 2026. Source: Customer Establishment_2026-07-27_09-59-43.pdf — three diagrams: Hub As-Is, Hub To-Be, BZ/WHC As-Is.
S1
BT internal actor split — Sales Specialist and Establishment Team
The swim lane shows three distinct BT roles: Sales Specialist (initiates CRF, commercial), Establishment Team (provisions systems — Tollring, FMS, SDS, EIM, VEL, BZ), Platform Admin (configures entitlements). The prototype had one "BT Wholesale Admin" persona conflating all three. Two new personas added: btSalesSpec and btEstablishment.
P1Done
S2
Org-level ordering readiness — EIM gate
An org can be portal-registered, users invited, roles assigned — but still unable to place orders until EIM (Enterprise Information Management) attributes are confirmed. eimStatus field (pending / confirmed / failed) added to orgs. Amber ordering-blocked banner shown when not confirmed.
P1Done
S3
API account is org-level, not a user role
Hub To-Be diagram: Strategic Portal creates customer account + API account as one atomic step at establishment. Previously modelled as "API Developer" user role only. apiAccountProvisioned boolean added to orgs. btEstablishment can provision. Structural note added: "API access is an org-level entitlement set at establishment. Individual API Developer role grants follow."
P1Done
S4
Primary contact has downstream system significance
Primary Contact is mapped into One Siebel, SDED's, Billing Systems, FMS, and Tollring — not just a UI flag. Transfer wizard step 1 now shows the full list of affected systems with a 24-hour propagation note.
P1Done
S5
Org lifecycle state (Established → Testing → Live)
BT Support places a test order before the welcome pack is sent — there's an implicit pre-live testing state. orgStatus field (established / testing / live) added. Status chip in org header. btEstablishment sees "Promote to live" button when in testing.
P2Done
S6
FMS sub-permissions: View / Block / Unblock
FMS has its own permission tier: View, Block, Unblock for resellers. BT holds Super Reseller level. The prototype previously modelled FMS as binary (on/off). Sub-permission checkboxes now visible when FMS is enabled for an org, with BT Super Reseller note.
P2Done
S7
SDS / CDR & EDR access entitlement
SDS (Call Detail Records / Event Detail Records) is a distinct entitlement with its own access identifier, confirmed at establishment. Previously invisible in the prototype. New capability row added with note: "Gated by SDS identifier confirmed at establishment."
P2Done
S8
Fault Diagnostics User — distinct named role for SVMP
SVMP access is provisioned for a specific nominated individual at establishment — separate from the Support Agent role. Added as a new BT-side role with "Nominated at establishment" badge and no standard assign button. Credentials delivered separately from standard invite flow.
P2Done
S9
KCI notification contacts — MSO / PEW per user
Specific named users are registered for MSO (Major Service Outage) and PEW (Planned Engineering Works) alerts at establishment — a notification entitlement separate from their role. MSO + PEW toggles added to the user drawer Notifications section.
P2Done
S10
Org pending/approval states
Credit vetting, CRF validation, and contract confirmation can all block org establishment. orgApprovalStatus field (pending_credit / pending_crf / approved) added. Pending orgs show amber chip in org list and banner in detail. btEstablishment sees "Approve and proceed" button.
P2Done
S11
Permission Sets sequencing — must exist before user invite
CUG creation is a prerequisite before users can be set up in the legacy BZ system. Strategically, Permission Sets must be configured before inviting users — otherwise users have no capabilities. Invite wizard now shows amber warning if the org has no Permission Sets configured.
P2Done
S12
Org setup checklist — btEstablishment view
8 parallel setup activities must all complete before go-live: Billing account / EIM attributes / FMS account / SDS access / Tollring account / VEL access / Training completed / Test order placed. 8-item interactive checklist added to org detail for btEstablishment persona, with progress bar and "Ready for go-live" banner.
P2Done
S13

Billing account validation includes credit rating (Red/Amber/Green risk classification). RAG status affects what the org is permitted to do — Red may restrict high-value ordering. ragStatus chip added to org detail. Red orgs show a restriction banner.

RID (Reseller Identifier) and CRN (Company Registration Number) are collected at establishment and gate ordering capability. Added as fields on org data, shown in the Identifiers section of Contact details for BT personas. ridConfirmed status chip included.

Blind spots

Areas the prototype doesn't model at all — not blocked, just not yet in scope. Worth flagging before detailed design.
B1
API consumer RBAC scopes
The prototype has an API Developer role and API key management UI, but doesn't model how API keys map to permission sets or what scopes an API consumer gets. This is the intersection with Matthew Lindley's API workstream.
Blind spot
B2
Multi-tenant data isolation
The prototype shows who can see what in the UI but doesn't model or surface how data leaks between orgs are prevented at the API/data layer. A reseller admin theoretically can't see another reseller's data — but this isn't shown or enforced in the prototype.
Blind spot
B3
Role inheritance across org tiers
PRD Section 17.5 mentions a three-layer model but is silent on whether permissions cascade down the org tree. If a Reseller Admin grants a role, does that role also apply within their child orgs? The prototype doesn't model this.
PRD Section 17.5
Blind spot
B4
Offboarding / removal cascade
What happens to open orders, active faults, and billing queries when a user is permanently removed? The prototype treats removal as a user-only action but in practice it may need to reassign or close linked records. No design exists for this yet.
Blind spot
B5
Org terminology changing — "Partner" and "Partner Organisation"
New — raised 27 Jul (Zoya Azar): The terms sub-reseller, child reseller, and dealer are being deprecated. The new simplified model uses just two terms: Partner and Partner Organisation. Permissions still differ between org types under the hood, but the UI labelling and language needs updating across the prototype. Impacts org type chips, type filter, type picker in invite wizard, and all copy referencing those terms.
Action needed
B6
Named-user vs role-based access model (Tollring / SVMP)
The swim lane reveals that some system accesses (Tollring, SVMP/fault diagnostics) are assigned to specific named individuals from the CRF — not to whoever holds a given role. The prototype models access as purely role-based. This is an architectural model gap: the prototype needs a way to show user-specific, non-role-based access grants that are set at establishment and don't transfer when a user changes role.
Blind spot
B7
Duplicate org / company check at account creation
Hub To-Be shows an explicit "Check Duplicates" step before the customer account is created — verifying no existing account exists for the same legal entity (CRN / RID). The Strategic Portal has no modelled mechanism to surface or prevent duplicate accounts. This step happens during BT-led onboarding (out of scope for the admin portal) but the underlying data model question — how the system flags two orgs with the same CRN — has no design yet.
Blind spot
